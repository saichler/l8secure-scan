- **Fixed directly in the PRD (§13, the scan-loop poll query) — L8Query enum-comparison syntax bug, verified against `l8ql`'s actual parser/interpreter source, not just precedent.** The PRD previously specified `select * from ScanJob where status='JOB_STATUS_QUEUED'` — a *quoted enum name string*. This does not work: `l8ql/go/gsql/interpreter/comparators/Equal.go` (`eqIntMatcher`/`getInt64`) does `strconv.Atoi` on the right-hand operand whenever the left-hand property is an `int32`-kind (enum) field; a quoted name like `'JOB_STATUS_QUEUED'` fails `Atoi` and the match silently returns `false` (not an error — the poll loop would just never match anything, a silent no-op bug). No enum name→int resolution exists anywhere in the WHERE-clause match path. Verified real precedent across `../l8erp` (`dashboard-config.js`: `status=2`), `../l8alarms` (`matcher.go`: `fmt.Sprintf("...Status=%d", ...)`) — every real query in the ecosystem filters enum fields with a **bare integer**, never a quoted name. PRD §13 now reads `select * from ScanJob where status=1` (`1` = `JOB_STATUS_QUEUED` per `proto/secscan.proto`, Phase 1), with the reasoning inlined in the PRD itself so Phase 3 doesn't need to rediscover it. **This same rule applies to any other enum-field WHERE clause introduced in later phases** (e.g. filtering `ScanStatus`/`Severity`) — always compare enums as bare integers, never quoted string names, even if a future PRD edit or ad-hoc query reintroduces the quoted form.

- **Fixed directly in the PRD (§10, `VulnRep`) — a real cross-tenant data leak in the original design, verified against `l8services`' actual request-dispatch source, not just precedent.** The PRD originally specified `VulnRep` as "no request body needed beyond auth ... via the standard row-level deny rule". Verified against `l8services/go/services/manager/ServiceManager.go`: row-level `ScopeView` filtering runs in exactly two places (`Handle`/`TransactionHandle`), both *after* a handler's `Get`/`Post` returns, keyed off the caller's `AAAId` carried on the inbound `ifs.Message`. A custom action-service (`VulnRep`, correctly modeled on `l8services/go/services/csvexport/CsvExport.go` — `IServiceHandler`, not `IServiceCallback`) only ever receives `Post(elems ifs.IElements, vnic ifs.IVNic)` — no `*ifs.Message`, and neither `IVNic` nor `IElements` expose the caller's identity anywhere. Worse, the natural implementation (copying `CsvExport.Post`'s own direct in-process `handler.Get(...)` call to fetch `ImageGroup` rows) bypasses `ServiceManager.Handle` entirely, so `ScopeView` never runs on it at all — it would return **every customer's** `ImageGroup` rows to any caller, not just the requester's own tenant. There is no framework extension point to recover caller identity inside a custom action-service handler (the same underlying gap as the already-accepted `ServiceCallback` limitation in §4/§9, now confirmed to extend to `IServiceHandler` too). Fixed the only workable way, consistent with this PRD's own existing v1 trust boundary: `VulnRep`'s request now carries an explicit trusted `customerId` (same pattern as every other write in this PRD), and the handler filters `select * from ImageGroup where customerId='<given>'` explicitly rather than relying on scoping that cannot actually reach this code path. Also corrected the response shape from a bogus "raw `text/csv` HTTP body" (no real precedent for that exists anywhere in the framework — verified) to a JSON response with the CSV text as a string field, reusing `l8api.L8CsvExportResponse{csv_data, filename, row_count}` — the actual, only real precedent for a generated-CSV response in this ecosystem. **This same caller-identity gap applies to any future custom `IServiceHandler`-based action service** (not just `VulnRep`): never assume automatic row-scoping reaches a hand-written `Post`/`Get` handler — it only ever protects the outer CRUD `Get` path through `ServiceManager.Handle`. `ImgRefAdd` was already unaffected — its every internal query already filters explicitly by the request's own trusted `customerId`, never relying on caller-derived scoping.

- **Fixed directly in the PRD (§13.1, scan loop) — re-scanning an `ImageRef` would have accumulated stale `ImageRefCve` findings forever.** Nothing in the original design deleted a previous scan's finding rows before writing a new scan's — §11.4's findings table (`baseWhereClause: imageRefId='<id>'`) would silently show old-plus-new findings mixed together after every re-scan, not just the latest scan. Fixed: `secscan-scanner` deletes every existing `ImageRefCve` row for the `imageRefId` (via `handler.Delete` with an L8Query, the real DELETE-by-query pattern — verified against `../l8alarms/go/alm/archiving/engine.go`'s `deleteAlarm`, the only real precedent for `IServiceHandler.Delete` usage in the ecosystem: `object.NewQuery("select * from X where field='value'", resources)` → `handler.Delete(elems, vnic)`) *after* Trivy succeeds and its output parses, but *before* writing the new findings — so a failed scan attempt leaves the previous scan's findings intact instead of wiping them for nothing. `l8common` has no `DeleteEntitiesByQuery` convenience wrapper (unlike `GetEntitiesByQuery`/`PutEntity`/`PostEntity`) — added one in `go/secscan/common/` mirroring the same hasLocal/`vnic.Request` fallback shape as the real helpers it sits next to, not a new pattern.
- **Verified (not a deviation, but a load-bearing architectural fact for Phase 3): `secscan-scanner`'s vnic calls to the backend are not actually AAA-checked.** See the corresponding note now in the PRD itself (§14, right after the `scanner-svc` paragraph) for the full verified call chain. In short: a raw vnic call with no explicit token gets an `aaaid` that's always too short to pass `CanDoAction`/`ScopeView`'s validated-token-length check, and both have an explicit "internal/system calls bypass" short-circuit for that case — confirmed against `../probler`'s `collector` binary (the closest real precedent: a separate-process, non-ORM worker) doing the exact same zero-login vnic calls this project's scanner does. **Practical upshot for Phase 3's code**: `secscan-scanner`'s `main.go` needs no login/credential step at all — `l8common.CreateResources` + `vnic.NewVirtualNetworkInterface` + `Start`/`WaitForConnection`, exactly like every other binary in this project, then straight into `common.GetEntity`/`PutEntity`/`PostEntity`/`GetEntitiesByQuery` calls. The `scanner`/`scanner-svc` role and user in `secscan.json` remain correct as *documentation* of intent and cost nothing to keep, but don't expect them to be doing any actual enforcement against this binary's traffic — the real boundary is which pods can reach the vnet (a Phase 7/K8s network-policy concern, not an application-auth one).
- **Phase 3 implementation notes**:
  - `go/secscan/scanner/pollworker/` — the generic harness (PRD §13's `pollworker.Run(query, claim, work)` sketch). Real signature ended up needing explicit `ServiceName`/`ServiceArea` alongside the query text (`l8common.GetEntitiesByQuery` requires them for handler routing; the query text alone isn't enough). Built on the two real `l8utils/go/utils/workers` primitives — `Workers{NewWorkers(limit)}` (bounded, `Run(IWorker)`, blocks when the pool is full, but no built-in wait-for-completion) and a plain `sync.WaitGroup` added around it for the fan-in half (`l8utils` doesn't have one primitive that's both bounded *and* fan-in — `MultiTask.RunAll()` is fan-in but unboundedly parallel, `Workers` is bounded but fire-and-forget; combining `Workers`+`WaitGroup` gets both, verified this is a normal/expected combination, not a workaround). Each poll tick: query, dispatch matches through `claim` (nil = always process, e.g. the resolver loop) then the bounded pool, wait for the batch to finish, sleep until the next tick.
  - `go/secscan/scanner/resolver/` configures the harness with `claim=nil` and a `work` function using `github.com/google/go-containerregistry` (`crane`'s underlying `pkg/v1/remote`/`pkg/name`/`pkg/authn` packages — not vendored anywhere else in the ecosystem yet, added fresh; `remote.WithAuthFromKeychain(authn.DefaultKeychain)` reads registry credentials from the pod's standard Docker config, matching §13/§18's "credentials already present on the pod") to fetch the image config and read its `Created` timestamp.
  - `go/secscan/scanner/scanloop/` configures the harness with `claim` = an unconditional `QUEUED→RUNNING` `PutEntity` (matches the PRD's already-accepted "no compare-and-swap, single replica" design — not re-litigated here) and a `work` function that itself fans out across the job's `imageRefIds` using a second, inner `Workers`+`WaitGroup` pool (two levels of bounded concurrency: across claimed jobs at the harness level, across one job's images at the work-function level — matches §13.1 step 1's phrasing that the per-image loop is itself "the harness's work function"). Shells out to `trivy image --format json <target>` (`repoName:tag` or `repoName@digest`, never the PRD's literal shorthand `repoName:<tag or digest>` — digests use `@`, not `:`, a plain notational fix, not a design change) via `os/exec`, parses just the fields needed (`Results[].Vulnerabilities[].{VulnerabilityID,PkgName,InstalledVersion,FixedVersion,Severity,Title}`) into a local struct rather than importing any Trivy Go package (Trivy is invoked as an external CLI per §13, not linked as a library). Trivy's occasional `"UNKNOWN"` severity string has no matching `secscan.Severity` bucket (enum zero must stay invalid, per `ProtobufRules`) — those findings are dropped (not counted, no `Cve`/`ImageRefCve` row), not force-mapped into `LOW`.
