- **Fixed directly in the PRD (§13, the scan-loop poll query) — L8Query enum-comparison syntax bug, verified against `l8ql`'s actual parser/interpreter source, not just precedent.** The PRD previously specified `select * from ScanJob where status='JOB_STATUS_QUEUED'` — a *quoted enum name string*. This does not work: `l8ql/go/gsql/interpreter/comparators/Equal.go` (`eqIntMatcher`/`getInt64`) does `strconv.Atoi` on the right-hand operand whenever the left-hand property is an `int32`-kind (enum) field; a quoted name like `'JOB_STATUS_QUEUED'` fails `Atoi` and the match silently returns `false` (not an error — the poll loop would just never match anything, a silent no-op bug). No enum name→int resolution exists anywhere in the WHERE-clause match path. Verified real precedent across `../l8erp` (`dashboard-config.js`: `status=2`), `../l8alarms` (`matcher.go`: `fmt.Sprintf("...Status=%d", ...)`) — every real query in the ecosystem filters enum fields with a **bare integer**, never a quoted name. PRD §13 now reads `select * from ScanJob where status=1` (`1` = `JOB_STATUS_QUEUED` per `proto/secscan.proto`, Phase 1), with the reasoning inlined in the PRD itself so Phase 3 doesn't need to rediscover it. **This same rule applies to any other enum-field WHERE clause introduced in later phases** (e.g. filtering `ScanStatus`/`Severity`) — always compare enums as bare integers, never quoted string names, even if a future PRD edit or ad-hoc query reintroduces the quoted form.

- **Fixed directly in the PRD (§10, `VulnRep`) — a real cross-tenant data leak in the original design, verified against `l8services`' actual request-dispatch source, not just precedent.** The PRD originally specified `VulnRep` as "no request body needed beyond auth ... via the standard row-level deny rule". Verified against `l8services/go/services/manager/ServiceManager.go`: row-level `ScopeView` filtering runs in exactly two places (`Handle`/`TransactionHandle`), both *after* a handler's `Get`/`Post` returns, keyed off the caller's `AAAId` carried on the inbound `ifs.Message`. A custom action-service (`VulnRep`, correctly modeled on `l8services/go/services/csvexport/CsvExport.go` — `IServiceHandler`, not `IServiceCallback`) only ever receives `Post(elems ifs.IElements, vnic ifs.IVNic)` — no `*ifs.Message`, and neither `IVNic` nor `IElements` expose the caller's identity anywhere. Worse, the natural implementation (copying `CsvExport.Post`'s own direct in-process `handler.Get(...)` call to fetch `ImageGroup` rows) bypasses `ServiceManager.Handle` entirely, so `ScopeView` never runs on it at all — it would return **every customer's** `ImageGroup` rows to any caller, not just the requester's own tenant. There is no framework extension point to recover caller identity inside a custom action-service handler (the same underlying gap as the already-accepted `ServiceCallback` limitation in §4/§9, now confirmed to extend to `IServiceHandler` too). Fixed the only workable way, consistent with this PRD's own existing v1 trust boundary: `VulnRep`'s request now carries an explicit trusted `customerId` (same pattern as every other write in this PRD), and the handler filters `select * from ImageGroup where customerId='<given>'` explicitly rather than relying on scoping that cannot actually reach this code path. Also corrected the response shape from a bogus "raw `text/csv` HTTP body" (no real precedent for that exists anywhere in the framework — verified) to a JSON response with the CSV text as a string field, reusing `l8api.L8CsvExportResponse{csv_data, filename, row_count}` — the actual, only real precedent for a generated-CSV response in this ecosystem. **This same caller-identity gap applies to any future custom `IServiceHandler`-based action service** (not just `VulnRep`): never assume automatic row-scoping reaches a hand-written `Post`/`Get` handler — it only ever protects the outer CRUD `Get` path through `ServiceManager.Handle`. `ImgRefAdd` was already unaffected — its every internal query already filters explicitly by the request's own trusted `customerId`, never relying on caller-derived scoping.

This directly validates `group-detail.js`'s own category-save call (`PUT {imageGroupId, categoryId}` only, no other `ImageGroup` fields) — flagging the verification itself since getting this wrong would have been a silent, spec-compliant-looking bug (blanking `imageName`/`imageRefCount`/etc. on every category change) that nothing in this phase's static checks could have caught.
- **Phase 4 implementation notes**:
  - Two `Layer8DModuleFactory.create()` calls share ONE `Layer8ModuleConfigFactory` namespace (`'SecScan'`, matching the PRD's own §11 snippet exactly) but use different `sectionSelector`/`defaultModule`/`initializerName` per section (`vulnmgmt`, `admin`) — verified this is safe (re-registering submodules/CRUD/forms-facade twice under the same namespace is idempotent) by reading `layer8d-module-factory.js` directly, not assumed from the single-section precedent (`../l8alarms` only ever has one section, so this exact 2-section-1-namespace shape had no direct precedent either).
  - `SecScan._showDetailsModal`/`_openAddModal` are overridden in `secscan-init.js` (the real `SpecialCases` "Custom CRUD Handlers" pattern) to route `ImageGroup` row-clicks to the custom Group Detail popup and `ImageCategory` adds to a custom customerId-injecting popup — verified the override actually takes effect by tracing `onRowClick` back to `layer8d-service-registry.js:110`'s `moduleNS._showDetailsModal(...)` dynamic lookup (not a captured reference at construction time, so a later override always wins).
  - The dashboard KPI strip's four numbers are each a separate `limit 1 page 1` query, reading `metadata.keyCount.counts.Total` (the same pagination-metadata mechanism `Layer8DTablePaginationMetadata` documents) rather than fetching and counting all rows client-side — "total pending scans" interpreted as `ImageRef.scanStatus=1` (images awaiting scan), "total critical CVEs" as a raw `ImageRefCve.severity=4` row count (not distinct CVEs) — both reasonable readings of intentionally-terse PRD wording, not verified against any more specific spec.
  - `Layer8DWidget.renderEnhancedStatsGrid` (the function the guide-lines doc points at for a KPI strip) turned out to be hardcoded to a different app's own `DashboardStats.navigateToSection` convention and a literal `value=0` — read its source before using it, and used the lower-level `Layer8DWidget.render(kpi, value, opts)` directly instead, once per real computed KPI number.
  - Category name resolution on the `ImageGroup` table (`categoryId` → name/color) is a client-side cache (`category-cache.js`), loaded once per section-entry — this ORM has no join (§8, verified in Phase 1/2), and `ImageGroup` carries no denormalized category name of its own. A row rendered before the cache populates shows "Uncategorized" until the next natural re-render; a minor, self-correcting cold-load race, not a functional gap.
