- **Flagged for Phase 3 (Scanner) and Phase 4/5 (UI) — L8Query enum-comparison syntax bug in the PRD, verified against `l8ql`'s actual parser/interpreter source, not just precedent.** PRD §13 (line ~516) specifies the scan-loop poll query as `select * from ScanJob where status='JOB_STATUS_QUEUED'` — a *quoted enum name string*. This does not work: `l8ql/go/gsql/interpreter/comparators/Equal.go` (`eqIntMatcher`/`getInt64`) does `strconv.Atoi` on the right-hand operand whenever the left-hand property is an `int32`-kind (enum) field; a quoted name like `'JOB_STATUS_QUEUED'` fails `Atoi` and the match silently returns `false` (not an error — the poll loop would just never match anything, a silent no-op bug). No enum name→int resolution exists anywhere in the WHERE-clause match path. Verified real precedent across `../l8erp` (`dashboard-config.js`: `status=2`), `../l8alarms` (`matcher.go`: `fmt.Sprintf("...Status=%d", ...)`) — every real query in the ecosystem filters enum fields with a **bare integer**, never a quoted name. For `secscan`, `JobStatus_JOB_STATUS_QUEUED = 1` (per `proto/secscan.proto`, Phase 1), so the correct query is `select * from ScanJob where status=1` (or the Go enum constant formatted as `%d`, not `%s`/quoted). This same rule applies to any other enum-field WHERE clause introduced in later phases (e.g. filtering `ScanStatus`/`Severity`) — always compare enums as bare integers, never quoted string names, regardless of what the PRD prose shows.
- **Flagged for Phase 4/5 (UI) — reminder to apply `L8QueryRules` precisely, since the PRD itself doesn't spell out every literal query string.** The PRD only gives literal L8Query text for the security deny rules (§4/§14) and the two nested `baseWhereClause` list views (§11.3/§11.4, `imageGroupId='<id>'` / `imageRefId='<id>'` — string-ID quoting there is correct, verified against `layer8m-portal.js`'s `baseWhereClause` construction).
