## 3. Ground rules while executing

- **The PRD is the already-approved plan.** Do not re-litigate its architecture or ask for re-approval of the overall approach. If you find a genuine gap, contradiction, or something that turns out not to work once you're actually implementing it, record it in `PROGRESS.md` and ask the user how to resolve it — do not silently deviate or "fix" something you don't understand yet.
- **Three design decisions in this PRD are deliberate, verified against actual framework source — not bugs to "fix":**
  1. `customer_id` on writes is a trusted client-supplied value (from the UI session), not server-validated. `IServiceCallback` has no access to caller identity in this framework — confirmed by reading `l8types/go/ifs/ServiceLevelAgreement.go` and `l8services/go/services/base/BaseService*.go`. This is an accepted v1 trust boundary (§4/§9 of the PRD), not something to patch.
  2. `secscan-scanner` runs as a single replica for v1. `l8services`' "2-phase commit" is a write-replication protocol, not a job-claim/lock primitive (verified against `l8services/go/services/transaction/states/*.go`) — do not "fix" the single-replica limitation by inventing a claim mechanism; that was already tried and found unsound.
  3. Vulnerability findings are `Cve` (global catalog) + `ImageRefCve` (per-image, customer-scoped) Prime Objects — never an embedded `repeated` struct field on `ImageRef`. This was verified against `l8orm/go/orm/stmt/QueryToSql.go`: a child/nested table only gets the query's `WHERE`/`ORDER BY` applied when it is the query's own root type; otherwise it's an unfiltered full-table read. Do not "simplify" this back into an embedded field — that would silently reintroduce an unbounded read on every vulnerability-detail view.
- **Never touch `l8types/go/ifs/`** or any other sibling project's source to work around a limitation — per `FrameworkInterfaceBoundaries`, flag it in `PROGRESS.md` and ask instead.
- **Never edit `vendor/`**, never run `go mod tidy/vendor/init`, per `VendorAndGit`.
- Follow `CleanupTestBinaries`: never `go build ./path/to/main/`; use `go build ./...` or `-o /dev/null`.
- Only implement what your phase covers. Don't reach ahead into later phases' scope even if it seems convenient.
